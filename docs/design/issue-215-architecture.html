Issue 215 — a killed worker's evidence

Design pass for issue 215 in udin-io/ex_athena, written before any code, off origin/main at fe2f5fb (issue 216 merged as PR 218 an hour earlier). Session 5906635b743d ran 3h36m over 17 workers and 9.1M input tokens and failed while all four of its deliverables sat finished on disk, because a worker's evidence dies with the worker. The issue proposes three layers — attach provenance to failures, write a per-worker NDJSON journal, push a derived summary and offer a pull tool. This page shows what the code already does, corrects six things the issue body gets wrong about it, and decides which of the three layers to build before any is written.

Headline. The incident the issue is named after does not need the journal. A worker that stops on error_max_input_tokens returns a complete %Result{} with its messages intact (loop.ex:177); ExAthena.Provenance can read it today and simply is not asked to. Layer 1 is one line and fixes the post-mortem in full. The journal is worth building for a different gap the issue does not name — see section 5, question 1.

The composition point is SpawnAgent, not the loop. The issue says the journal "subscribes to the loop's existing on_event stream — the same stream the Coordinator already consumes". There is no stream. on_event is a single 1-arity callback with exactly one holder, and attribute_events/6 overwrites it with fn event -> sink.(sub_id, event) end whenever the parent carries an :agent_event_sink. So the journal is composed, not subscribed, and it must be composed in do_execute/5 after attribute_events/6 has had its say — that is also the only place that knows the sub_id the journal is named after. The issue's real economy ("no new instrumentation in the loop") survives intact: loop.ex is untouched.

5. The five design questions

Q1 — does the journal need to exist at all?

Yes, but narrowly, and only after layer 1. There are four distinct ways a worker's evidence is lost today and the journal is the right answer to exactly one of them.

Loss modeWhat survives todayCheapest fix
Worker returns a %Result{} with an error finish_reason — the reported incident Everything: messages, conclusions, todos. layer 1a one line
Deadline kill, Coordinator attached (web UI) %AgentInfo{} in memory: todos, conclusions, and a 30-row transcript_tail whose tool_call rows name the files. layer 1c read the rows progress_digest/2 throws away
Deadline kill or crash, no Coordinator (CLI, headless, tests) Nothing. A Sidechain line reading result: nil. layer 2 — the journal, and nothing else reaches this case
The parent itself dies — its linked Task.Supervisor collapses the whole subtree Nothing. Sidechain.write/1 never runs; the Coordinator marks agents failed and retires after 5 minutes. layer 2 — and here the reader is a human, not an orchestrator

The fourth row is the honest case for building it. Every fact in this document was recovered by reading source, because session 5906635b743d left no machine-readable record of what its seventeen workers touched. A journal's first customer is the post-mortem; the orchestrator is its second. That is still worth building — but it argues for a small, boring, durable file, not for a rich event log.

Q2 — write-path safety: what is actually guaranteed

The issue's conclusion is right and its reason is not. Three separate things get conflated as "flushing".

  • File.write(path, line, [:append]) opens, writes and closes per call. When it returns, the bytes are in the OS page cache and visible to every other process on the machine. Losing them needs a machine crash or power loss, not a process kill and not a BEAM exit. There is no fsync — state that plainly rather than implying durability the code does not buy.
  • :delayed_write does not simply lose data on kill. The buffer lives behind the file handle and is flushed on close, at 64 KB, or after 2 seconds; killing the owner closes the port, which attempts that flush. The real defect is different and worse for this use: a reader cannot see the buffer. The parent reads the journal microseconds after Task.shutdown(task, :brutal_kill) returns, and any write error at close is discarded because nobody holds the handle to observe it. So: no :delayed_write — but for visibility and ordering, not for flushing.
  • A torn final line is possible either way. :kill lands between reductions, so a BIF already inside write(2) completes; but a process killed between formatting a line and writing it loses that line outright. NDJSON is the right format precisely because it degrades one line at a time. The reader must Jason.decode line by line and drop an undecodable last line without raising. That is a testable requirement, not a caveat.

Cost of writing this way: two extra syscalls per line, on the worker's own scheduler, inside its on_event callback — which is called synchronously, in the worker process (Events.emit/2). At roughly four journalled events per iteration over a 25-iteration budget that is about 100 writes per worker. Negligible, provided :content and :thinking are excluded. And because the callback runs in the worker, the writer must be try/rescue-guarded — a filesystem boundary, the same exemption Sidechain.write/1 already takes.

Rejected: a separate journal GenServer fed by cast. It would take the filesystem off the worker's scheduler, and it survives the worker's death well enough to drain its mailbox. But it reintroduces the exact race the journal exists to remove in the case that matters most: when the parent dies, the journal process dies with it and every unflushed cast is a line that was never written. It buys back on the order of 100 microseconds per worker. Inline and synchronous wins.

Q3 — cost, and the two Tuning knobs

Two keys, both integers, both under :agents. The repo's convention for "off" on an integer knob is 0, so no boolean key is needed: journal_bytes: 0 disables journalling entirely.

KeyDefaultMinSettings-modal field and why the number
:agents, :journal_line_chars4001 "Worker journal line cap (characters)" — cap on the digested arguments in one journal line. 400 is not a new judgement: it is agents.transcript_entry_chars, the existing cap on the same information in AgentInfo.append_transcript/2. One number, two places.
:agents, :journal_bytes2_000_0000 "Worker journal size cap (bytes)" — 0 disables journalling. A write line is about 120 B; a bash line with a 400-char command digest about 500 B. A 25-iteration worker making four calls per iteration writes roughly 100 lines, about 30 KB. 2 MB is a runaway guard at ~60x the worst worker this session produced, not a budget.

Both keys need a field in lib/ex_athena/web/settings.ex. This is enforced, not conventional: test/ex_athena/web/settings_test.exs:158 ("schema coverage") greps Path.wildcard("lib/**/*.ex") for literal Tuning.get(:ns, :key calls and fails on any that the schema does not declare. All twelve existing :agents keys are covered; these make fourteen.

On reaching journal_bytes the writer stops and appends one final {"ev":"journal_truncated"} line so the reader knows it holds a prefix. Never rotate. A rotated journal throws away its beginning — which is the part naming what the worker built.

Q4 — the push summary

Do not add a new [worker evidence] line. Provenance.footer/1 is already the ~400-char derived summary, it already rides back on every successful hand-back, and Provenance.scan/1 parses that exact text back out of a transcript — the moduledoc calls it "a parsing contract, not merely display". A second format for the same facts is a second contract to keep in sync. Extend the existing footer with byte sizes:

[worker provenance] files changed: plan/uat_testing/guides-96-114-extract.md (85,043 B) | commands run: mix test (failed), git status
  • Every hand-back, success and failure — not failures only. "The worker produced nothing" is exactly as much a fact as "the worker produced 85 KB", and a footer that appears only on failure teaches the model that its absence means success. It is already unconditional on the success path; layers 1a and 1c make it unconditional on the other three.
  • Sizes come from File.stat/1, in the parent's cwd, at hand-back. That is what makes it evidence: "wrote an 85 KB file" is checkable, "the file is structurally complete" is a claim.
  • When the file is gone, say so — never omit the row. An omitted path reads as "the worker wrote nothing", which is the failure this issue exists to stop. Two cases, two renderings: (missing) when the path simply is not there, and (85,043 B journalled; worktree removed) when the journal recorded a size and finalize_isolation/1 has since deleted the directory. For a :worktree worker the second is the normal case, because finalize_isolation/1 runs above the result case — see the warning in section 3.
  • No new cap key. The footer is already bounded by agents.provenance_max_listed (15 paths) and agents.provenance_command_chars (120). Sizes add about 10 characters per path.

Q5 — retention

There is no pruning path. Not for the journal, and not for the sidechain transcripts that already exist: .exathena/sessions/PARENT_ID/sidechains/*.jsonl grows for the life of the checkout. The issue's "lives and is pruned with its session" describes a mechanism that was never built.

The precedent to copy is ExAthena.Checkpoint.Sweeper: a one-shot boot Task under the application supervisor, restart: :transient, that File.rm_rfs .exathena/file-history/SESSION_ID directories older than 30 days, best-effort and logged at info level. Generalising it to take a list of {subdir, max_age} pairs and adding .exathena/sessions is a handful of lines.

It belongs in its own ticket. It fixes unbounded growth that predates this issue and applies to data this issue does not create, and bundling it here means this PR deletes files no reviewer asked it to touch. Ship 215 writing into an unpruned directory — as Sidechain already does — and prune both in one follow-up.

6. Layer 3b — one tool, two sources

ReadWorkerReport was built in PR 218 to be extended here. Its moduledoc says so: "add its source and the filter: / tail: options HERE rather than introducing a parallel path." The argument name, the id validation (@id_re, which refuses anything not matching subagent_[A-Za-z0-9_-]{1,64} rather than sanitising it) and the cwd/session path resolution are all shared. Add to the existing tool:

  • source — "report" (default, unchanged behaviour) or "journal".
  • filter — "writes" / "commands" / "errors" / "tail", with n for tail. Journal source only.
  • The existing from / max_chars paging and the "no report on disk for ID" error stay as they are.

Share the directory, not the file

Path: .exathena/sessions/PARENT_ID/journal/SUBAGENT_ID.ndjson — a sibling of sidechains/, resolved by the same cwd-plus-session-id join report_path/2 already performs. (The issue's <run_dir>/workers/ names a root that does not exist: run_dir appears nowhere in lib/ or test/.)

The repo's DRY rule demands asking whether Sidechain should simply be extended instead. It should not, and the reason is mechanical rather than aesthetic:

SidechainJournal
Writerthe parent, once, after the worker is already gonethe worker, continuously, while it is alive
Lifetimea single line at the end of the spawnthe whole run of the worker
Dies withthe parentnothing — that is the point
Contentthe worker's prose report, untruncateddigested facts about what it did

And one hard blocker: ReadWorkerReport.read_last_line/1 takes the last line of sidechains/ID.jsonl as the report. Appending journal events into the same file makes every read_worker_report call return a journal event instead of the report — silently breaking the tool PR 218 just shipped. Separate files, shared directory.

The DRY-compliant outcome is smaller than merging them: Sidechain grows a public session_dir/2, and Journal and ReadWorkerReport both call it, so there is one definition of where a worker's artifacts live instead of the three string joins there are today.

Which events are written, and which are refused

EventRateJournalled as

Correlation happens at read time, not write time

%ToolResult{} carries tool_call_id and no tool name (lib/ex_athena/messages.ex:35). The issue's sample line puts "name":"write" on the result, which the writer cannot know without holding per-worker state across callback invocations. Write id on both lines and let the reader join them. A stateless closure is a closure that cannot lose state when the worker dies.

The one derivation worth doing at write time is the byte count: the journal runs in the worker's own process and cwd, so a File.stat/1 on the path a successful write just named is taken at the one moment the file certainly exists — including inside a :worktree worker's directory, which finalize_isolation/1 deletes before the parent could ever stat it.

Why 1b is a stat, not a parser

The issue offers two routes for bash-written files and prefers "have the bash tool report the paths it touched". That is more robust if the tool can know, and it cannot without paying for it: discovering what an arbitrary command touched means an strace, a directory scan, or a git status --porcelain before and after every single bash call. The ui_payload at bash.ex:405 is a clean place to put the answer; nothing cheap produces one.

Parsing shell syntax to find write targets is the other rabbit hole, and it is worse, because a wrong answer here is a fabricated fact in a footer whose entire value is that its facts are checkable. Redirection into a variable, tee behind a pipe, sed -i, a Python heredoc that opens its own file — the tail is endless and every miss is silent.

The narrow version keeps the property that matters. Match only unambiguous forms — > path, >> path, tee path — then File.stat/1 every candidate and report only the ones that exist with a size. False negatives stay possible and are acceptable: a footer reading files changed: none is the status quo. False positives become impossible, because a path that does not exist is never reported. A parse that must survive a stat cannot invent evidence.
