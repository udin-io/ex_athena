Issue 215 — a killed worker's evidence

Design pass for issue 215 in udin-io/ex_athena, written before any code, off origin/main at fe2f5fb (issue 216 merged as PR 218 an hour earlier). Session 5906635b743d ran 3h36m over 17 workers and 9.1M input tokens and failed while all four of its deliverables sat finished on disk, because a worker's evidence dies with the worker. The issue proposes three layers — attach provenance to failures, write a per-worker NDJSON journal, push a derived summary and offer a pull tool. This page shows what the code already does, corrects six things the issue body gets wrong about it, and decides which of the three layers to build before any is written.

Headline. The incident the issue is named after does not need the journal. A worker that stops on error_max_input_tokens returns a complete %Result{} with its messages intact (loop.ex:177); ExAthena.Provenance can read it today and simply is not asked to. Layer 1 is one line and fixes the post-mortem in full. The journal is worth building for a different gap the issue does not name — see section 5, question 1.

The composition point is SpawnAgent, not the loop. The issue says the journal "subscribes to the loop's existing on_event stream — the same stream the Coordinator already consumes". There is no stream. on_event is a single 1-arity callback with exactly one holder, and attribute_events/6 overwrites it with fn event -> sink.(sub_id, event) end whenever the parent carries an :agent_event_sink. So the journal is composed, not subscribed, and it must be composed in do_execute/5 after attribute_events/6 has had its say — that is also the only place that knows the sub_id the journal is named after. The issue's real economy ("no new instrumentation in the loop") survives intact: loop.ex is untouched.

Ordering trap found while reading, not in the issue. In do_execute/5, finalize_isolation/1 runs above the result case, so a :worktree worker's directory is already git worktree remove --force'd by the time the success branch calls append_provenance/2. Any stat the footer performs against a worktree worker's paths therefore finds nothing. Either the sizing moves ahead of finalize_isolation/1, or the footer falls back to the size the journal recorded at write time and labels it as such: 85,043 B (journalled; worktree removed). That is a second argument for the journal the issue does not make.
