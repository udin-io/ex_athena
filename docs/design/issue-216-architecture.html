Issue 216 — a worker finishes, the orchestrator dies anyway

Design pass for issue 216 in udin-io/ex_athena, written before any code. Session 5906635b743d ran 3h36m over 17 workers and 9.1M input tokens, then terminated on error_consecutive_mistakes with all four deliverables complete on disk. The issue carries four fixes across SpawnAgent, ReAct, Provenance and BudgetPressure; that trips the architecture gate, so this page shows what already exists, what each fix adds, and where the issue describes the code wrongly. It decides the mechanism for item 1 and the scope of item 2 before implementation starts. Branches off fix/worker-token-budget (PR 214), which owns BudgetPressure.

3. Item 1 — a failure the model reads but the loop does not score

What the counter actually does today

Two independent things happen to a tool error in Modes.ReAct, and item 1 needs to separate them:

  • do_execute/2 line 353 builds Messages.tool_result(id, "error: …", true) AND calls bump_mistake/1. Both, from one clause.
  • At the turn boundary (line 213) the bump is clamped to at most one per turn, then any_tool_success?/1 (line 433) resets the counter to zero if ANY tool result in the turn has is_error != true.
  • Loop.loop/1 line 167 ends the run at max_consecutive_mistakes.

The issue's preferred option would silently do the opposite of what it wants. any_tool_success?/1 tests err != true. An is_error: :informational satisfies that, so the turn would be counted as a SUCCESS and the counter would RESET to zero — precisely the defect the issue rejects option 2 for. Option 1 is not "prefer 1 over 2"; as written it is option 2 with extra blast radius.

Audit verdict: NO. The third state is not safe as specified. Fourteen sites, of which five change behaviour and three of those change it wrongly — including the one function item 1 exists to fix. Three more work only because :informational happens to be truthy, which is a property of Elixir, not a decision anyone recorded. And the field is PERSISTED (session.ex:737) and sent on the wire (req_llm.ex:444), so a third state is a data-format change for a loop-accounting problem.

Recommendation — carry the signal on the RETURN, not on the message

Keep is_error a boolean. Add one tool return shape: {:error, :uncounted, text}.

The tool-result message stays exactly as it is today — is_error: true, red in both UIs, wire is_error: true, masked by the compactor, rejected by Provenance, and read by the model as a plain failure. Only ReAct.do_execute/2 changes: a new clause that builds the same error result but skips bump_mistake/1. any_tool_success?/1 already returns false for is_error: true, so the turn is neither a success nor a mistake with no edit at all. Zero of the fourteen audit rows move.

  • Where the decision is made: SpawnAgent's failure branch (spawn_agent.ex:390) classifies sub_result.finish_reason and returns {:error, :uncounted, text} for a budget termination, plain {:error, text} otherwise.
  • Contract debt to pay while there: ExAthena.Tool's @callback execute/2 (tool.ex:59) already omits the {:ok, text, ui} shape that ReAct has handled for some time. The new shape goes in the spec alongside it.

Do NOT key the decision on Terminations.category/1

category/1 returns :capacity for eight subtypes, and three of them are the worker MISBEHAVING rather than running out of room: error_consecutive_mistakes, error_no_progress, and error_max_structured_output_retries. A worker that hallucinated its way to its own mistake ceiling, or went in circles, is exactly the case the parent's counter should catch — item 3 of this same issue records a worker that died that way. Keying on category/1 would make all three uncountable.

Use an explicit list of budget-exhaustion subtypes instead: error_max_input_tokens, error_max_budget_usd, error_max_turns, error_prompt_too_long, error_thinking_starved, and the timeout path. Everything else keeps counting. Terminations.category/1 has no production caller today other than Result.category/1, which itself has none, so nothing forces the reuse.

Second thing the issue gets wrong about its own session. It says the last three spawns died on error_max_input_tokens, error_during_execution and error_max_input_tokens, then proposes exempting category :capacity. error_during_execution is :retryable — so under the issue's own rule the middle one still counts, the counter goes 0, 1, 1, and the run survives anyway. The rule works; the narrative that all three were capacity does not. The acceptance test must therefore be written with three budget terminations, not "the three from this session".

What still stops a parent looping on bad spawns

An uncounted failure neither bumps nor resets, so a parent that spawns nothing but budget-dying workers is no longer bounded by the mistake counter. It is still bounded by: Agents.Quota (max_agents_per_run, default 24), Agents.Deadline (the run deadline, refused at spawn_agent.ex:234), the max_input_tokens and max_budget_usd guards, error_no_progress, and orchestrate's own repeat-objective watchdog (orchestrate.ex:588). That is five rails; the counter was never the load-bearing one for this shape.

4. Item 2 — the report is already on disk; only the address is missing

Where it is written today

Agents.Sidechain.write/1, called unconditionally at spawn_agent.ex:368 before either result branch, writes one JSON line to:

cwd/.exathena/sessions/PARENT_SESSION_ID/sidechains/SUBAGENT_ID.jsonl

The line carries prompt, a serialised opts, and for a successful loop return text (untruncated), finish_reason, iterations, tool_calls_made, duration_ms, cost_usd, conclusions and todos. Worker Ut1hUSMB's 21,697-character extraction was written there in full, at the same moment the parent was being handed 2,000 characters of it.

Prerequisite bug — the sidechain of a worktree-isolated worker is deleted moments after it is written. Line 368 passes cwd: Keyword.get(sub_opts, :cwd, ctx.cwd), which for an agent declaring isolation: :worktree is the ephemeral worktree under ~/.cache/ex_athena/worktrees/…. Line 381 then calls finalize_isolation/1, which runs git worktree remove --force on that same directory. Write, then delete, eleven lines apart. Fix is one argument: write the sidechain under the PARENT's ctx.cwd. This must land before the retrieval tool, or the tool will 404 for exactly the isolated workers most worth reading.

What item 2 actually needs

  1. Fix the cwd above. One line.
  2. Name the address in the truncation notice. truncate_result/2 (spawn_agent.ex:971) currently ends with "Ask for the specific part you still need; do not re-request the whole thing" — an instruction with no tool behind it. It becomes a concrete call: read_worker_report("SUBAGENT_ID", from: 2000). Note the signature change: truncate_result/2 is called from three places and only one of them knows a subagent_id, so the notice needs the id threaded in (or a /3 arity with the current behaviour as the default).
  3. Add the retrieval tool. read_worker_report(subagent_id, from:, bytes:), orchestrator-scoped the way spawn_agent is, resolving ctx.cwd/.exathena/sessions/ctx.session_id/sidechains/SUBAGENT_ID.jsonl, decoding the line, and returning a byte slice of result.text with its own cap. The id must be validated against the session's own spawns, not interpolated into a path — it comes from the model.
  4. Call append_provenance/2 on the failure path too (it is called only at line 440 today, inside the success branch — the issue is right about this one). Then the failure message names the files the worker's tool calls prove it wrote.

Overlap with issue 215. 215's read_worker_log(subagent_id, filter) reads a per-worker NDJSON journal at run_dir/workers/SUBAGENT_ID.ndjson — a different file, a different writer, the same argument and the same resolution logic. Build one tool: ship it here as read_worker_report over the sidechain, and have 215 add its filter:/tail: options and the journal source to that tool rather than introducing a second one. Whoever implements 215 inherits the id-validation and path-resolution code instead of writing it twice. If 215 lands first, this item is its report filter and should not be built at all.

5. Item 3 — refuse a write brief handed to a read-only agent

Where the check goes

The effective toolset is computed by resolve_tools/3 (spawn_agent.ex:1024), called at line 308 — which is after Quota.claim/1 has already taken a worker off the run's allowance of 24. Quota has no release. A refusal placed at the natural site therefore burns a slot for a spawn that never ran, and the module's own doc says "a refusal costs nothing". The check must run in execute/2's cond (alongside the depth and completed-todo rails, lines 189-212), which means resolving the agent definition's declared tools there — resolve_agent/2 is cheap and has no side effects, so this is a reorder, not a duplication.

Proposed detection rule

Refuse when both hold:

  1. Capability. The resolved toolset (after resolve_tools/3) contains none of write, edit, bash, and no tool the host registered as mutating. Derived from the toolset, never from the agent's name — a custom read-only agent gets the same rail, and an explore a user has granted write to does not.
  2. Intent. The brief text — prompt plus objective plus expected_output, the three fields @prompt_sources already reads — matches an explicit instruction to produce a file. Anchored on an imperative verb immediately governing a file object, case-insensitive: (write|save|create|output|put|append) … (the|your|a) (result|output|report|findings|file|it) … to … plus a bare path-shaped token, and the literal forms write the result to a file, write to PATH, create the file, save it to.

The refusal names the agent's actual tools and the alternative, in the grammar the depth and quota rails already use:

not started: agent "explore" has tools read, glob, grep, lsp, web_fetch,
web_search, usage_rules — none of which can write a file, and your brief asks
for one ("WRITE THE RESULT TO A FILE"). Delegate this to "implementer", or
drop the file requirement and ask explore to report in its reply.

False-positive cost, stated plainly

  • A refused spawn costs the orchestrator one turn and nothing else: no quota slot (given the reorder above), no worker time, no tokens beyond the error line. The three existing refusal rails already establish that price.
  • The realistic false positive is a brief that says "read the config file and write up what you find" — write up is prose, not a file instruction. The anchored form above does not match it, because up is not a file object and no path token is present. Verbs like document, describe, note, list are not in the verb set.
  • The route around a false positive is one word in the brief, and the error names it. That is cheaper than the measured cost of the false negative: 24.6 minutes and 540K input tokens, plus two probe workers, one of which died on its own mistake counter.

This is the item I would consider splitting out. Items 1, 2 and 4 are loop accounting and reporting and share two files. Item 3 is a natural-language classifier on model input — a different kind of risk, a different kind of test, and the only one of the four whose correctness is a judgement call rather than a behaviour. It also has a cheaper 80 percent available first: explore's system prompt does not currently say "you cannot write files; if the brief asks you to write one, say so and stop" — only the orchestrator's protocol says it, to the wrong party. Adding that line to priv/agents/explore.md is a one-line change that would have caught this session, and the code rail can follow on its own ticket with the regex it deserves.

6. Item 4 — the BudgetPressure note

Loop.BudgetPressure.build_note/1 on branch fix/worker-token-budget. The directive to verify is NOT in this note and is NOT being touched — the note is about what to do when the budget cannot pay for everything left. Today it names one state; it must name two.

Today

[runtime] You are N turns in and near the end of your budget. Todos: D of T
completed. If you cannot finish everything, reduce scope NOW: stop gathering,
complete what you can, and produce your report. State explicitly which todos
you did NOT complete and what remains for each, so the orchestrator can
re-delegate them as separate steps. An honest partial report is worth far more
than being cut off mid-exploration.

Proposed

[runtime] You are N turns in and near the end of your budget. Todos: D of T
completed. Verifying your work is still your job — but it is now the FIRST
thing to cut, not the last. Pick the state you are in:

- Deliverable NOT yet produced: reduce scope NOW. Stop gathering, produce what
  you can, and state explicitly which todos you did NOT complete and what
  remains for each, so the orchestrator can re-delegate them as separate steps.

- Deliverable produced but NOT fully verified: hand it back NOW, in this turn.
  Do not start another verification pass — a pass you do not survive loses the
  report as well as the check. Open your report with UNVERIFIED, name the
  artifact and where it is, and list the checks you did not run so the
  orchestrator can re-delegate verification as its own cheap step.

An honest partial report is worth far more than being cut off mid-exploration,
and an unverified artifact the orchestrator knows about beats a verified one it
never hears about.
  • What does not change: the trigger (wrap_up_at_percent, default 75), the three budget fractions, the ephemeral tail placement, and todo_progress/1.
  • What does: build_note/1 only. No new state is read, so no new plumbing — the worker classifies its own state, which is the only party that can.
  • Why "the FIRST thing to cut" rather than "skip verification": the three quoted workers each knew they were near the ceiling and each chose one more pass anyway. The note has to rank the two actions, not just list them. Telling a worker verification is optional in general would trade a visible failure for a silent one — which is what the issue says, and this wording keeps it.
